# 工作区 AI 文档瘦身治理提示词

> 可移植的一次性任务提示词,让任意主机的 Agent 对其 Claude Code 工作区文档做系统性瘦身治理。源自 2026-07-05 对 `/Users/yb/OpenSource` 的实战(hub 开局注入 28.4k→约 7k token,14 个项目 CLAUDE.md 归位)。

以下整段复制给目标主机的 Agent 即可:

```markdown
# 任务:工作区 AI 文档瘦身与防膨胀治理

对本机的 Claude Code 工作区文档做一次系统性瘦身治理。逐阶段执行,先调查后动手,全程零丢失。

## 原理(先理解再执行)

三个机制事实(来自 Claude Code 官方文档):
1. 工作区/全局 CLAUDE.md 与 auto-memory 的 MEMORY.md **每个会话开局全量注入**——每个字都是重复付费的固定开销;单个 CLAUDE.md 超过 200 行后指令遵循度显著下降(写得越多,规则越不被听见)。
2. MEMORY.md 只加载前 200 行或 25KB(先到为准),超出部分**静默截断**——往末尾追加的新记忆会悄悄失效。
3. 子目录 CLAUDE.md 是**懒加载**的(Claude 读到该目录文件时才注入)——细节下沉到子项目是零开局成本的。

膨胀机理(治理时逐条针对):
- "一行索引"没有硬性长度约束时,AI 在"怕丢信息"与"守格式"之间总选前者,把千字写成不换行的"一行"。
- 文件现状比规则更有示范力:一行 500 字的旧条目会教出一行 600 字的新条目(破窗效应)。
- 多处记账:同一项目状态往往同时记在工作区索引/MEMORY.md/memory 子文件/项目 CLAUDE.md/项目 STATUS.md 多处,每处都在膨胀且互相矛盾。

治理原则:**hub 只做路由表,细节下沉懒加载,历史归 git log 与归档区,"怕丢"的解法是下沉+指针而不是塞索引,防复发靠 lint 不靠自觉。**

## 第一阶段:盘点(只读,不改任何文件)

1. 测量开局注入的文件:`~/.claude/CLAUDE.md`、工作区根 CLAUDE.md、`~/.claude/projects/<路径编码>/memory/MEMORY.md`(路径编码=工作区绝对路径把 `/` 换成 `-`)。用 `wc -lc` 记录行数/字节。
2. 检查 MEMORY.md 是否接近或超过 25KB 截断线——超线属于救火优先级。
3. 找多处记账:抽 2–3 个项目,数同一项目的状态信息出现在几个文件里。
4. 项目级摸底:`find <工作区>/projects -maxdepth 3 \( -name "CLAUDE.md" -o -name "STATUS.md" \) | xargs wc -c | sort -rn`,找超 200 行或塞满带日期进度史的。
5. 找根目录僵尸文档(带日期的一次性计划/交接文档,任务早已完成)。
6. 把发现汇报给用户(数字+结论),**等确认后再进第二阶段**。若本机文档本来就干净(hub 合计 <10KB 且无多处记账),直接汇报"无需清理"并结束。

## 第二阶段:零丢失备份

- `mkdir -p <工作区>/_archive`;工作区 CLAUDE.md 和 MEMORY.md 各 cp 一份带日期快照(如 `CLAUDE-YYYY-MM-DD-pre-slim.md`)。
- 项目级动刀前逐个查 `git -C <项目> status --porcelain -- CLAUDE.md`:git-clean = 旧版在 git 历史里可恢复;**非 git 仓库或有未提交改动的,先 cp 到 _archive/ 再动**。
- 发现"非 git 仓库"的活跃项目要单独向用户报告(这是比文档膨胀更大的风险)。

## 第三阶段:hub 瘦身

- **MEMORY.md**:删除与工作区 CLAUDE.md 重复的项目索引区;每条记忆压成一行钩子 `[标题](子文件.md) — 钩子(≤40字)`;压缩前确认对应 memory 子文件已含细节,缺的先下沉再压;顶部加预算注释(≤150 行/12KB)与归档指针。
- **工作区 CLAUDE.md**:项目索引行只留白名单字段——名字/路径/一句话定位(≤30字)/状态标签;禁日期/版本号/功能清单/成就形容词;参考类条目(vendor 等)压成分组列表;删除"子项目规则文件清单"类章节(懒加载机制使其无意义)。

## 第四阶段:规则落地(防复发,写进工作区 CLAUDE.md)

写入四节(若已存在则核对,不重复写):
1. **信息归属矩阵**:项目定位/技术栈/怎么跑 → 项目 CLAUDE.md;进度/下次入口/待决策 → 项目 STATUS.md;开发史 → git log + STATUS 底部归档区;跨项目经验 → memory 子文件(MEMORY.md 一行钩子)。
2. **文档预算**:工作区 CLAUDE.md ≤200 行/10KB;MEMORY.md ≤150 行/12KB;项目 CLAUDE.md ≤200 行(不放带日期状态);STATUS.md 主体 ≤100 行(历史进底部归档区)。超预算 = 先瘦身下沉再写入,禁止直接追加。
3. **更新协议**(自下而上、越往上越薄):项目 STATUS.md(详细)→ 项目 CLAUDE.md(仅项目本身变了)→ 工作区索引行(仅状态标签变了)→ memory(仅跨项目经验);禁止同一段话写进两处;每 1–2 周跑 consolidate-memory 做 lint。
4. **文档写作红线**:①时态——CLAUDE.md 只写现在时(半年后仍成立),STATUS.md 写现在完成时,过去时只进 git log/归档区;②索引行钩子是"让下个会话决定要不要点进去",不是替它读完;③写入前自检:这条的唯一归属地?目标文件超预算没?会写得比周围条目长吗?;④写入前看周围条目格式,遇超长旧条目先修剪再写——你的条目就是下一个 AI 的模板。
(如有详细开发手册文档,把带好/坏示例的完整写作指南放那里,hub 只留红线+指针。)

## 第五阶段:项目级外科手术(逐个活跃项目的 CLAUDE.md)

判断标准 = 时态。
**保留**(现在时/耐用):定位、技术栈、目录结构、开发命令、代码约定、变现方案、活跃文档清单、首次运行记录(压缩为:日期+环境+耐用坑+指向 STATUS.md)、GitHub 发布记录(仓库/目录映射/推送方式)、踩坑沉淀。
**剥离**(过去时/状态):带日期的验证战报(BUILD SUCCEEDED/N 单测全绿/live 截图清单)、"迭代 1/2/3 完成了什么"编年史、"待办/下一步"区(归 STATUS.md;这类区常有与同文件其他章节矛盾的过期条目,是多处记账烂掉的标志)。
特殊情况:
- 剥离前确认 STATUS.md 已覆盖同等信息,缺的先补进 STATUS.md。
- CLAUDE.md 超长但超的是**参考材料**(测试规范/示例代码/CI 配置)→ 拆到 docs/ 子文档,原处留 3 行摘要+指针(懒加载,用到才读)。
- **团队共享仓**(upstream 有其他维护者的 AGENTS.md/CLAUDE.md)一律不动。
- 顺手修明显笔误(重复行等),但不做超范围重构。

## 第六阶段:验证与汇报

- `wc -lc` 全部改动文件,确认各自预算内。
- 汇报:前后对比表(hub 开局注入字节数)、每类手术的项目清单、备份/可恢复路径、发现的额外风险(无版本控制的项目、超预算的 STATUS.md 清单——后者不必本次处理,留给后续会话按更新协议顺手治理)。

## 红线

- 不动任何密钥/凭证内容;不动业务数据目录;团队共享仓的规范文件不动。
- 所有删除都必须有 git 历史或 _archive 备份兜底。
- 若发现本工作区已做过同样治理(CLAUDE.md 已有"文档预算"节),只做增量 lint,不重复大改。
```

## 关键结论

- 提示词设计为"先盘点汇报、经确认再动手",可安全丢给任意主机的 Agent。
- 三个机制事实(200 行遵循度衰减 / MEMORY.md 25KB 静默截断 / 子目录懒加载)是整套治理的依据,新主机上若 Claude Code 版本行为有变,先核对官方 memory 文档。
- 零丢失策略分级:git-clean 靠 git 历史,非 git 仓/脏文件先拷 `_archive/`。
- 项目级手术的判断标准是"时态":现在时保留,过去时剥离,参考材料拆子文档。
- 防复发靠三件套:预算数字(可执行)、更新协议(单一来源)、定期 consolidate-memory lint。
